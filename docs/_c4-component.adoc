== Components

Zooming into the *Edigen CLI Application* container reveals the internal components
and the direction of data flow between them. Each Java package maps onto one
component; the AST model is the shared data structure that the passes and generators
operate on.

=== Component responsibilities

[cols="1,1,3",options="header"]
|===
| Component | Package | Responsibility

| CLI / UI Layer | `net.emustudio.edigen`, `net.emustudio.edigen.ui`
| `Edigen` is the `main()` entry point; it prints messages, maps exceptions to exit
  codes, and delegates to `Translator`. `ui.CommandLine`, `Argument` and `Help`
  parse arguments into a `Map<Setting,String>` and render usage. This layer keeps
  the compiler core independent of the command line.

| Translator | `net.emustudio.edigen.Translator`
| The application core. Opens the specification, invokes the `Parser`, runs the
  fixed pass pipeline over the AST, and finally runs the two generators. Its
  `transform(...)` method is the authoritative definition of pass order.

| Parser | `net.emustudio.edigen.parser` (generated from `Grammar.jj`)
| Recognizes decoder and disassembler syntax and constructs AST nodes with source
  line numbers. It deliberately does *not* resolve names or normalize structure –
  that is the job of the passes.

| AST Model | `net.emustudio.edigen.nodes`
| The shared tree. `Specification` is the root and always contains a `Decoder` and a
  `Disassembler` subtree. All nodes extend `TreeNode`, which provides parent/child
  links (insertion-ordered), in-place mutation, deep `copy()`, and `dump(...)`.

| Transformation Passes | `net.emustudio.edigen.passes`
| Thirteen `Visitor` subclasses that validate the specification and rewrite the
  decoder subtree into a decision tree. Detailed in <<Code>>.

| Code Generators | `net.emustudio.edigen.generation`
| `DecoderGenerator` and `DisassemblerGenerator` (both extend `Generator`) compute
  template variables and delegate code fragments to emitting visitors
  (`GenerateFieldsVisitor`, `GenerateMethodsVisitor`, `GenerateFormatsVisitor`,
  `GenerateParametersVisitor`).

| Templating | `net.emustudio.edigen.misc`
| `Template` replaces `%name%` variables (with block-variable indentation support);
  `PrettyPrinter` indents emitted Java line-by-line; `BitSequence` supports bit-level
  computations used by the passes.
|===

=== The Visitor mechanism

Every analysis, validation, transformation and emission step is a subclass of the
base `Visitor`. The base implementation simply traverses children, so each concrete
visitor overrides only the node types it cares about. This is the central extension
mechanism: adding a new pass usually means adding one `Visitor` subclass and slotting
it into `Translator.transform(...)`, without touching the node classes.
